# Architecture backend (hôte C#)

L'hôte est une application C# .NET 10 avec une fenêtre WinUI 3 (Windows App SDK, non empaquetée) qui héberge une seule WebView2. Il ne porte aucune interface métier : il gère la fenêtre, les terminaux, la persistance et les services locaux. L'interface entière est dans `web/`.

## Projets

| Projet | Rôle |
| --- | --- |
| `src/Dock.Core` | Bibliothèque sans interface, testable : pseudo-consoles, Job Objects, intégration shell, modèle et persistance de session. Aucune dépendance WinUI. |
| `src/Dock.Host` | Fenêtre WinUI 3, WebView2, pont hôte / web. Contient le moins de logique possible. |
| `tests/Dock.Core.Tests` | Tests xUnit de `Dock.Core` (voir `docs/TESTING.md`). |

`Directory.Build.props` à la racine fixe `Nullable`, `ImplicitUsings`, la plateforme x64 et `win-x64`.

Règles :

- L'hôte est la source de vérité de la session persistée : le web envoie la session complète, l'hôte la valide avant d'écrire. Chaque `session.save` ou `text.save` répond `session.saved`, ou `session.saveFailed {message}` (session refusée, disque ou droits) sans faire tomber la session en cours.
- Au démarrage, `app.hello` porte `recovery` quand `session.json` ou `text.json` a été mis en quarantaine ; la session de secours est alors la session initiale et le fichier fautif reste à côté pour récupération.
- Le texte restauré n'est qu'un affichage : les shells sont toujours relancés neufs, aucune commande n'est rejouée.
- `settings.export` ouvre un sélecteur d'enregistrement (`.json`, nom proposé `dock-preferences`) et écrit la configuration enregistrée ; `settings.import` ouvre un sélecteur de fichier `.json`, valide le contenu et renvoie `settings.imported` sans écrire, avec dans `warnings` chaque valeur de persistance hors bornes ramenée dans sa plage (`PersistenceSettingsModel.OutOfRangeWarnings`) : l'application effective passe par `settings.save`, ce qui vaut confirmation et remplace la configuration (aucune fusion). Un fichier refusé remonte en `error`.
- `settings.save` valide, écrit les quatre fichiers puis applique immédiatement : nouveaux chemins de shells pour les prochains `terminal.create` (les shells déjà lancés ne bougent pas), nouvelle commande d'éditeur, nouvelle racine des projets, nouvelle limite d'historique. Un réglage refusé remonte en `error` sans rien écrire.
- Chaque pane est rattaché à un Job Object avec `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` : fermer un pane (`terminal.close`), un onglet, un workspace ou l'application termine de force tout son arbre de processus, y compris les enfants détachés du shell. Aucun service persistant ne reprend les anciens agents ou serveurs.
- Avant une fermeture, le web demande `terminal.activity {panes}` ; l'hôte répond `terminal.activityResult` avec les panes qui ont encore des programmes actifs (noms de processus). Le web affiche alors une confirmation ciblée ; l'hôte n'arrête rien tant que le web n'envoie pas `terminal.close` ou `window.close`. `app.closing` porte directement cette activité pour tous les panes vivants.
- L'environnement transmis au shell ajoute `DOCK_TERMINAL=1`, `DOCK_PANE_ID` et `TERM_PROGRAM=DockTerminal`, et retire toute variable `WEZTERM_*`.
- États des agents : l'hôte purge `agents\*.json` au démarrage, à chaque `terminal.create` et `terminal.close` (aucun état ancien n'est restauré comme vivant), puis évalue `AgentMonitor.Resolve(_terminals.Probes())` hors du thread UI toutes les 2 s et au plus 150 ms après un changement du dossier `agents` (`FileSystemWatcher`, changements rapprochés regroupés en une seule évaluation). Il envoie `agent.states {panes[{paneId, agent, state, message?, detail?}]}` seulement quand le résultat change ; un pane absent de la liste n'a aucun agent. Le script `hooks\dock-agent-state.ps1`, copié à côté de `Dock.exe`, est le producteur Claude Code : appelé par les hooks `SessionStart` (inconnu), `UserPromptSubmit` et `PostToolUse` (en cours), `PreToolUse` limité par `matcher` à `AskUserQuestion`, `PermissionRequest` et `Notification` de type `permission_prompt`, `elicitation_dialog` ou `agent_needs_input` (en attente : une réponse est réellement requise ; la notification d'inactivité `idle_prompt` est ignorée pour ne pas confondre attente et fin de tour), `Stop` (terminé, avec en `detail` le dernier texte de Claude : `last_assistant_message` s'il est fourni, sinon la dernière réponse hors sous-agent parmi les 200 dernières lignes du transcript), `StopFailure` (en erreur), `SessionEnd` (suppression du fichier), il lit `DOCK_PANE_ID` hérité du shell et écrit le fichier du pane ; les messages sont des libellés français fixes (jamais le texte anglais de Claude), une notification d'attente n'écrase pas une attente déjà signalée par `PermissionRequest`, et le script porte un BOM UTF-8 pour que Windows PowerShell 5.1 lise ses accents. `ClaudeHooksInstaller` (`Status`, `Install`, `Remove`) fusionne ou retire ces hooks dans `%USERPROFILE%\.claude\settings.json` uniquement sur `agents.installHooks` / `agents.removeHooks` (clic explicite dans Paramètres) : les autres clés et les hooks étrangers sont conservés, un groupe Dock est reconnu par le chemin de `dock-agent-state.ps1`, l'écriture est atomique ; un fichier illisible remonte en `error` sans être touché (ses commentaires JSON éventuels ne survivent pas à une réécriture). Chaque opération répond par un `settings.result` à jour. Codex CLI n'a pas de producteur : « Inconnu » seulement.
- Ne jamais réimplémenter `wtr` / `rmwt` : ils viennent du profil chargé par PowerShell.
- Contrat de synchronisation worktrees : l'hôte n'exécute aucun effet de `wtr` / `rmwt`. Après `wtr`, le prompt du pane émet OSC 7 avec le nouveau dossier (`terminal.cwd`), rien d'autre. Après `rmwt`, à chaque `terminal.cwd` reçu de n'importe quel pane, `TerminalManager.MissingDirectories` vérifie le dossier courant de toutes les sessions vivantes et l'hôte envoie `terminal.pathMissing {pane, path, fallback}` pour celles dont le dossier a disparu ; même message à `terminal.create` si le dossier demandé n'existe plus (le shell démarre alors dans le dossier utilisateur). Aucun pane ni workspace n'est fermé ou créé automatiquement.
- Un échec de `terminal.create` remonte en `error` avec le `pane` concerné ; le web affiche alors un état local au pane (relance, choix d'un autre shell, fermeture). Seul l'échec d'une commande `terminal.*` porte ce `pane` : une autre commande qui en cite un (`context.open`, `attention.raise`…) remonte en `error` sans lui, pour ne jamais présenter un shell vivant comme arrêté.

## Dock.Host

| Fichier | Rôle |
| --- | --- |
| `App.xaml.cs` | Fixe le dossier de données `%LOCALAPPDATA%\Dock` (remplacé par la variable `DOCK_DATA_DIR` quand elle est définie) et le dossier utilisateur WebView2 qu'il contient. |
| `MainWindow.xaml(.cs)` | Fenêtre ouverte maximisée (taille restaurée 1480 × 900), une `WebView2` qui l'occupe entièrement, aucun `KeyboardAccelerator`. Donne le focus clavier à la `WebView2` dès sa création, puis à chaque activation de la fenêtre : au démarrage, la saisie va au terminal actif sans clic préalable (un focus demandé avant la création de la WebView2 resterait sans effet). Active `AllowDrop` sur la WebView2 : sans lui, le contrôle WinUI ne transmet pas à la page les glisser venus d'autres applications, comme les fichiers de l'Explorateur déposés sur un terminal. Refuse toute navigation hors de l'origine de l'application (`NavigationStarting`) et toute nouvelle fenêtre (`NewWindowRequested`) : un fichier ou un lien déposé, un `window.open` ne peuvent ni remplacer l'interface ni ouvrir une fenêtre de navigateur. Désactive les raccourcis navigateur, mappe `https://dock.app/` sur `wwwroot/`, ou navigue vers `DOCK_WEB_DEV_URL` si la variable est définie (serveur Vite). À la fermeture par la fenêtre, annule une première fois (`Handled`) et laisse `HostBridge.RequestClose` envoyer `app.closing {activity}` au web ; la fermeture réelle vient de `window.close` renvoyé par le web (après envoi de la disposition et du texte) ou d'un délai de garde de 3 s. Quand des programmes sont actifs, le web envoie `window.closeCancel`, ce qui désarme le délai de garde le temps de la confirmation ; un second clic sur la croix pendant l'attente est ignoré. |
| `Bridge/HostBridge.cs` | Reçoit les messages JSON du web (`WebMessageReceived`), route par `type`, renvoie par `PostWebMessageAsJson`. Regroupe la sortie des terminaux par pane et la vide sur le thread UI en une seule passe. ## Construction

- `dotnet build Dock.slnx` construit tout. La cible `BuildWeb` de `Dock.Host.csproj` lance `pnpm install` et `pnpm build` si `web/dist/index.html` est absent ou en configuration Release, puis `CopyWebToOutput` copie `web/dist` dans `wwwroot/` du dossier de sortie.
- Publication autonome : `dotnet publish src/Dock.Host/Dock.Host.csproj -c Release -r win-x64 -p:Platform=x64 --self-contained -o publish`. `EnableMsixTooling` est requis pour que le `.pri` soit publié.
- Installeur : `scripts/build-installer.cmd` lit la version de `Dock.Host.csproj`, publie dans `publish/`, télécharge le programme d'installation WebView2 Evergreen puis compile `installer/Dock.iss` avec Inno Setup 6 vers `installer/output/Dock-<version>-setup.exe`. Installation par utilisateur sans droits administrateur (`%LOCALAPPDATA%\Programs\Dock`, élévation proposée en option), WebView2 installé seulement s'il manque, raccourci dans le menu Démarrer et raccourci Bureau optionnel. À la désinstallation, `Dock.exe --remove-claude-hooks` retire les hooks Dock de `settings.json` de Claude Code s'il y en a (`ClaudeHooksInstaller.RemoveIfPresent`, fichier non réécrit sinon), puis une question propose de supprimer `%LOCALAPPDATA%\Dock` (non par défaut, conservé en désinstallation silencieuse). L'installeur n'est pas signé : SmartScreen avertit au premier lancement.
- Release : monter `<Version>` dans `Dock.Host.csproj`, lancer le script, puis `gh release create v<version> installer/output/Dock-<version>-setup.exe --generate-notes`.
- Développement web à chaud : `pnpm dev` dans `web/`, puis lancer l'hôte avec `DOCK_WEB_DEV_URL=http://localhost:5173`.
- Instance isolée : `DOCK_DATA_DIR=<chemin absolu>` fait lire et écrire session, texte, réglages, états d'agents et profil WebView2 dans ce dossier. Indispensable pour lancer une version de développement pendant qu'un Dock installé tourne, sans écraser sa session.

## Conventions

- Messages d'erreur en français (les termes Git restent en anglais et invariables : push, pull, fetch, stash, stage, merge, rebase, amend, checkout, cherry-pick), suffixe `Model` pour les classes de données, suffixe `Async` pour les méthodes asynchrones, aucun commentaire dans le code, fichiers de moins de 400 lignes.
- Les erreurs attendues du pont remontent en `error` au web ; les exceptions inattendues ne doivent pas faire tomber l'hôte.
