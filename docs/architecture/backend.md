# Architecture backend (hôte C#)

L'hôte est un exécutable console C# .NET 10 (`Tily`), sans interface, lancé et piloté par le processus principal d'Electron (`desktop/`). Il échange des messages JSON, un par ligne, sur son entrée et sa sortie standard : ceux du web transitent par Electron sans transformation, ceux qui commencent par `host.` concernent Electron seul (fenêtre, notifications, ressources de l'aperçu, panes navigateur). Il ne porte aucune interface métier : il gère les terminaux, la persistance et les services locaux. L'interface entière est dans `desktop/renderer/`, la fenêtre et ses vues dans `desktop/`.

## Projets

| Projet | Rôle |
| --- | --- |
| `backend/src/Tily.Core` | Bibliothèque sans interface, testable : PTY Unix, arbre de processus, intégration shell, modèle et persistance de session. Ne cible que macOS (libc, libproc) ; seule dépendance externe : `Microsoft.Data.SqlClient`, pour répliquer une base SQL Server de worktree. `AllowUnsafeBlocks` est requis par les `LibraryImport`. |
| `backend/src/Tily.Host` | Exécutable console `Tily` : boucle de messages, pont hôte / web, flux de chaque domaine. Contient le moins de logique possible. Référence `Tily.Mcp` et `Tily.Pty`, publiés dans le même dossier. |
| `backend/src/Tily.Mcp` | Exécutable console `tily-mcp` : serveur MCP stdio (SDK `ModelContextProtocol.Core`) lancé par Claude Code, qui relaie chaque outil à son instance de Tily par le canal de `Tily.Core/Mcp` : `tily_layout`, `tily_read_pane`, `tily_commands`, `tily_wait_for` (`TilyTools`, arguments bornés avant envoi, version annoncée lue sur le `Tily.dll` voisin), `tily_open_workspace`, `tily_new_tab`, `tily_split`, `tily_focus`, `tily_rename`, `tily_run`, `tily_interrupt`, `tily_close` (`TilyActions`, dossiers et commandes vérifiés avant envoi), `tily_worktrees`, `tily_create_worktree`, `tily_remove_worktree` (`TilyWorktreeTools`, dépôt par défaut : dossier courant de l'agent), `tily_browser_open`, `tily_browser_navigate`, `tily_browser_reload`, `tily_browser_resize`, `tily_browser_console`, `tily_browser_network`, `tily_browser_screenshot` (`TilyBrowserTools`, adresse, emplacement, largeur, niveau et chemin de capture vérifiés avant envoi ; la capture est rendue à Claude en image PNG, avec ses détails en texte, et enregistrée dans le fichier `.png` demandé ; `TilyConnection.SendAsync` donne la réponse brute du pipe). Lancé hors de Tily (`McpEndpoint.PaneFromEnvironment` nul, faute de `TILY_PANE_ID`), il ne déclare ni outil ni instruction : rien n'entre dans le contexte de Claude. Il s'arrête quand Claude Code ferme son entrée standard, à la fin de la session. Lancé avec l'argument `hook` (`AgentHookCommand`), il sert de hook d'état à Claude Code au lieu de démarrer le serveur (voir États des agents). Référencé par `Tily.Host`, il est construit et publié dans le même dossier que `Tily` et partage son runtime .NET. |
| `backend/src/Tily.Pty` | Exécutable console `tily-pty` (`Program.cs` appelle `PtyLauncher.Run`) : lancé par `UnixPty` dans la nouvelle session du pane, il attache le terminal de contrôle, réinitialise les signaux puis se remplace par le shell (`execvp`). Référencé par `Tily.Host` et par les tests, publié à côté de `Tily`. |
| `backend/tests/Tily.Core.Tests` | Tests xUnit de `Tily.Core` (voir `docs/testing.md`). |

`backend/Directory.Build.props` fixe `Nullable`, `ImplicitUsings` et `LangVersion` ; tous les projets ciblent `net10.0`, la publication vise `osx-arm64`.

L'abandon exige une confirmation et produit le même enregistrement d'annulation que l'abandon d'un fichier. `GitStateReader` assemble l'état envoyé au web, worktrees compris (`WorktreeLister.TryList`, liste vide si `git worktree list --porcelain -z` échoue). Opérations (`GitChangeCommands`, `GitSyncCommands`, `GitBranchCommands`, `GitStashTagCommands`, `GitHistoryCommands`) : stage, unstage, abandon, commit, amend, marquer résolu (refusé si des marqueurs `<<<<<<<` / `>>>>>>>` restent, sauf confirmation), terminer ou abandonner l'opération en cours, push (vers l'amont, publication avec `--set-upstream` sinon, `--porcelain` pour reconnaître un refus), push forcé `--force-with-lease` accepté seulement après un refus et avec confirmation, pull (`--no-rebase` si ni `pull.rebase` ni `branch.<nom>.rebase` n'est configuré), fetch, merge, rebase sans mode interactif, cherry-pick (`-m 1` pour un commit de merge), reset soft / mixed / hard, checkout (branche locale, branche distante → branche locale suivie, commit → HEAD détachée), création, renommage et suppression de branches locales ou distantes, tags, suppression groupée de branches locales et distantes, de tags et de stash (`GitRefDeleteCommands` : tout est vérifié avant la première suppression, branche courante refusée, branches distantes supprimées d'abord par dépôt distant, puis `branch -D`, `tag -d` et les stash du plus ancien au plus récent ; Chaque opération renvoie un `GitOutcomeModel` (message en français avec les termes Git anglais, avertissement éventuel) et un `GitUndoRecordModel` que `GitUndoJournal` garde en mémoire, un par dépôt ; `GitUndo` défait la dernière opération faite depuis Tily (reset `--soft` pour un commit, `--keep` pour un merge, un pull, un rebase ou un cherry-pick, index restauré par `read-tree` pour un reset mixed, modifications locales restaurées depuis `stash create` pour un reset hard, checkout inverse, branche ou tag recréé à sa cible, stash réinséré par `stash store`, suppression groupée défaite étape par étape en ordre inverse (branches, tags et stash locaux, stash dans leur ordre d'origine ; les branches distantes supprimées ne sont pas restaurées), fichiers abandonnés réécrits depuis les blobs sauvegardés) et la refuse si le dépôt a changé depuis ou si un push a publié les commits entre-temps. |

Règles :

- L'hôte est la source de vérité de la session persistée : le web envoie la session complète, l'hôte la valide avant d'écrire. Chaque `session.save` ou `text.save` répond `session.saved`, ou `session.saveFailed {message}` (session refusée, disque ou droits) sans faire tomber la session en cours.
- Au démarrage, `app.hello` porte `recovery` quand `session.json` ou `text.json` a été mis en quarantaine ; la session de secours est alors l'avant-dernier enregistrement (`session.previous.json`, copié avant chaque écriture de `session.json` ; si cette copie échoue, l'écriture a lieu quand même et l'ancienne copie reste) s'il est valide, sinon la session initiale, et le fichier fautif reste à côté pour récupération. `AtomicFile` force l'écriture du fichier temporaire sur le disque (`Flush(true)`) avant de le renommer, pour qu'une coupure de courant ne laisse pas un fichier vide.
- Le texte restauré n'est qu'un affichage : les shells sont toujours relancés neufs, aucune commande n'est rejouée.
- `settings.export` et `settings.import` sont interceptés par Electron, qui ouvre le sélecteur (enregistrement `.json`, nom proposé `tily-preferences.json`, ou ouverture d'un `.json`) puis transmet `settings.export {path}` ou `settings.import {path}` ; l'hôte écrit la configuration enregistrée, ou valide le contenu et renvoie `settings.imported` sans écrire, avec dans `warnings` chaque valeur de persistance hors bornes ramenée dans sa plage (`PersistenceSettingsModel.OutOfRangeWarnings`) : l'application effective passe par `settings.save`, ce qui vaut confirmation et remplace la configuration (aucune fusion). Un fichier refusé remonte en `error`.
- `settings.save` valide, écrit les quatre fichiers puis applique immédiatement : nouveaux chemins de shells pour les prochains `terminal.create` (les shells déjà lancés ne bougent pas), nouvelle commande d'éditeur, nouvelle racine des projets, nouvelle limite d'historique. Un réglage refusé remonte en `error` sans rien écrire.
- Chaque pane est un PTY Unix dont le shell ouvre une nouvelle session : fermer un pane (`terminal.close`), un onglet, un workspace ou l'application envoie `SIGHUP` au groupe du shell puis `SIGKILL` au shell et à tout son arbre (`ProcessTree.Members` : descendants et processus attachés au même terminal), y compris les enfants détachés du shell qui gardent le terminal ; un processus qui a quitté la session (`setsid`, démon) n'est pas suivi. La fermeture du maître signale aussi la coupure au terminal. Aucun service persistant ne reprend les anciens agents ou serveurs.
- Avant une fermeture, le web demande `terminal.activity {panes}` ; l'hôte répond `terminal.activityResult` avec les panes qui ont encore des programmes actifs (noms de processus) et renvoie tel quel le numéro `request` reçu (0 sans numéro), qui distingue les demandes du serveur MCP de celles de la confirmation de fermeture. Le web affiche alors une confirmation ciblée ; l'hôte n'arrête rien tant que le web n'envoie pas `terminal.close` ou `window.close`. `app.closing` porte directement cette activité pour tous les panes vivants.
- L'environnement transmis au shell ajoute `TILY_TERMINAL=1`, `TILY_PANE_ID`, `TERM_PROGRAM=TilyTerminal`, `TERM` et `COLORTERM`, et retire toute variable `WEZTERM_*`. Electron transmet à l'hôte l'environnement du shell de connexion de l'utilisateur (`$SHELL -ilc env`), si bien que `PATH` contient Homebrew, `pnpm` ou `node` même quand Tily est lancé depuis le Dock. Un `TILY_DATA_DIR` défini est réécrit en chemin absolu au démarrage de l'hôte, pour que le hook et `tily-mcp`, lancés depuis un autre dossier, retrouvent la même instance.
- États des agents : l'hôte purge `agents/*.json` au démarrage, à chaque `terminal.create` et `terminal.close` (aucun état ancien n'est restauré comme vivant), puis évalue `AgentMonitor.Resolve(_terminals.Probes())` hors de la boucle de messages toutes les 2 s et au plus 150 ms après un changement du dossier `agents` (`FileSystemWatcher`, changements rapprochés regroupés en une seule évaluation). Il envoie `agent.states {panes[{paneId, agent, state, message?, detail?, interrupted?, sessionId?}]}` seulement quand le résultat change ; un pane absent de la liste n'a aucun agent. `tily-mcp hook` (`AgentHookHandler`, lancé avec l'argument `hook`) est le producteur Claude Code : appelé par les hooks `SessionStart` (inconnu), `UserPromptSubmit` et `PostToolUse` (en cours), `PreToolUse` limité par `matcher` à `AskUserQuestion`, `PermissionRequest` et `Notification` de type `permission_prompt`, `elicitation_dialog` ou `agent_needs_input` (en attente : une réponse est réellement requise ; la notification d'inactivité `idle_prompt` est ignorée pour ne pas confondre attente et fin de tour), `Stop` (terminé, avec en `detail` le dernier texte de Claude : `last_assistant_message` s'il est fourni, sinon la dernière réponse hors sous-agent parmi les 200 dernières lignes du transcript), `StopFailure` (en erreur), `SessionEnd` (suppression du fichier), il lit `TILY_PANE_ID` hérité du shell et écrit le fichier du pane (`.tmp` puis renommage) ; sans `TILY_PANE_ID` il ne fait rien et sort toujours avec le code 0, sans démarrer le serveur MCP. Un second groupe `PreToolUse`, `matcher` `Bash` filtré par `"if": "Bash(open *)"` (`ClaudeHooksInstaller.PreviewCommandCondition` : le hook n'est lancé que pour une commande dont une sous-commande est `open`), intercepte l'ouverture d'une page HTML. `ShellCommandSplitter` découpe la commande sur `&&`, `||`, `;`, `|`, `&` et les retours à la ligne (guillemets respectés, `2>&1` et `&>` non coupés, commentaires et corps des heredocs ignorés), puis `HtmlOpeningFinder` prend le premier segment `open [-a <application>] <chemin>.html` (`.htm` compris, chemin entre guillemets doubles, simples ou sans espace, `~/…`, absolu ou relatif au `cwd` du hook et aux `cd` qui précèdent ce segment). Une page existante dépose `previews/<pane>-<guid>.json` (écrit en `.tmp` puis renommé) et répond `permissionDecision: deny` avec une raison en français qui dit à Claude que Tily a ouvert le fichier et, dans une commande composée (le hook ne peut pas en laisser passer une partie), de relancer le reste sans ce `open` ; dans une commande composée, une page introuvable (produite par un segment précédent, `cd` non résolu) est refusée sans aperçu, avec la consigne de relancer le reste puis `open "<chemin>"` seul ; un `open` seul vers un fichier absent, une autre extension ou une commande sans `open` de page passent sans réponse ; les messages sont des libellés français fixes (jamais le texte anglais de Claude), et une notification d'attente n'écrase pas une attente déjà signalée par `PermissionRequest`. `ClaudeHooksInstaller` (`Status`, `Install`, `Remove`) fusionne ou retire ces hooks dans `~/.claude/settings.json` uniquement sur `agents.installHooks` / `agents.removeHooks` (clic explicite dans Paramètres) : chaque hook Tily est `{ "type": "command", "command": "<dossier de Tily>/tily-mcp", "args": ["hook"], "timeout": 5 }`, les autres clés et les hooks étrangers sont conservés, un groupe Tily est reconnu à son exécutable `tily-mcp` suivi du seul argument `hook`, `Status` exige chaque groupe attendu avec son `matcher` et son `if` (des hooks installés par une version antérieure sont donc annoncés « non installés » jusqu'à une nouvelle installation), l'écriture est atomique ; un fichier illisible remonte en `error` sans être touché (ses commentaires JSON éventuels ne survivent pas à une réécriture). Chaque opération répond par un `settings.result` à jour. Codex CLI n'a pas de producteur : « Inconnu » seulement.
- Serveur MCP : `McpFeed` lit l'état de la déclaration hors de la boucle au démarrage et n'ouvre le canal de l'instance que si le serveur est déclaré ; `mcp.install` / `mcp.remove` (clic dans Paramètres) déclarent ou retirent le serveur, ouvrent ou ferment le canal et répondent par `settings.result`. Chaque appel reçu sur le canal devient `mcp.request {id, tool, pane, arguments?}` vers le web ; la réponse `mcp.response {id, result | error}` le termine ; sans réponse en 10 s (pour `waitFor`, `McpWaitFor.AnswerTimeout` ; pour `run`, `interrupt` et `close`, qui peuvent attendre l'accord de l'utilisateur, `McpActions.ConsentAnswerTimeout` ; pour `createWorktree` et `removeWorktree`, `McpWorktrees.OperationAnswerTimeout` ; pour les outils navigateur longs, `McpBrowser.AnswerTimeout`), l'appel échoue en français ; avant `app.ready`, il échoue avec « Tily démarre encore ». La boucle ne fait que poster des messages : l'attente se fait sur le pool de threads. L'hôte ajoute la branche de chaque pane à la réponse de `layout`. Le pane appelant vient de `TILY_PANE_ID`, hérité par Claude Code puis par `tily-mcp`.
- Mises à jour : l'hôte vérifie la dernière release 10 s après le lancement puis toutes les 6 h tant que `updates.autoCheck` est vrai (réglage appliqué dès `settings.save`), et à chaque `update.check`, et annonce une version plus récente avec ses notes et la page des releases. Rien n'est téléchargé sans `update.install`, refusé en `error` pour une copie qui ne peut pas se mettre à jour (hors de `Tily.app` ou dossier de l'application protégé en écriture) ; l'installeur va dans le sous-dossier `updates` du dossier de données, vidé au démarrage. `update.apply` n'est accepté que si l'installeur vérifié existe encore (sinon `error` et retour à l'état « disponible ») : l'hôte retient alors l'installeur et répond `update.restart`, le web ferme l'application comme d'habitude (disposition et texte envoyés, puis `window.close`) et le script de `UpdateInstaller.Start` n'est lancé qu'à la fin de `HostBridge.Dispose`, terminaux arrêtés. Il attend la fin d'Electron, remplace `Tily.app` puis relance Tily. Aucun certificat Apple n'est requis.
- Worktrees : Tily en porte une version native (`Worktrees/`, `WorktreeFeed`) ; `wtr` / `rmwt` restent chargés par le profil et utilisables au terminal avec les mêmes chemins. L'hôte ne crée ni ne ferme jamais de workspace : il annonce `worktrees.created`, le web ouvre le workspace.
- Contrat de synchronisation worktrees : pour un `wtr` / `rmwt` tapé au terminal, l'hôte ne rejoue aucun effet. Après `wtr`, le prompt du pane émet OSC 7 avec le nouveau dossier (`terminal.cwd`), rien d'autre. Après `rmwt`, à chaque `terminal.cwd` reçu de n'importe quel pane, `TerminalManager.MissingDirectories` vérifie le dossier courant de toutes les sessions vivantes et l'hôte envoie `terminal.pathMissing {pane, path, fallback}` pour celles dont le dossier a disparu ; même message à `terminal.create` si le dossier demandé n'existe plus (le shell démarre alors dans le dossier utilisateur). Aucun pane ni workspace n'est fermé ou créé automatiquement.
- Un échec de `terminal.create` remonte en `error` avec le `pane` concerné ; le web affiche alors un état local au pane (relance, choix d'un autre shell, fermeture). Seul l'échec d'une commande `terminal.*` porte ce `pane` : une autre commande qui en cite un (`context.open`, `attention.raise`…) remonte en `error` sans lui, pour ne jamais présenter un shell vivant comme arrêté.

Création : `WorktreeCreator.Create` (dossier : `folder` de la demande, sinon celui mémorisé pour `project`, sinon celui des Paramètres), puis, si `rememberFolder`, le dossier du worktree est mémorisé pour le projet (`SettingsService.RememberWorktreeFolder` sur la boucle ; choisir le dossier des Paramètres oublie celui du projet), puis `PortRandomizer`, puis, si `remember`, enregistrement du dépôt principal comme dépôt par défaut du projet (`WorktreeProjectsRepository`, un échec ne produit qu'un avertissement), puis `worktrees.created {path, name, branch, install?}` dès que le dossier existe (le web ouvre le workspace et lance `install` dans son terminal), rafraîchissement de la vue Git, puis réplication de la base si demandée, pendant que `pnpm install` tourne. Chaque étape annonce `worktrees.progress {operation, message}` ; la fin envoie `worktrees.done {operation, message, warnings[]}` (message avec les ports et la base) ou `worktrees.failed {operation, step, message, output?, lockedBy?}`. |
| `Bridge/UpdateFeed.cs` | Commandes `update.*` routées par `HostBridge` et état des mises à jour, protégé par un verrou : `idle`, `checking`, `upToDate`, `available`, `downloading`, `ready`, `failed`, avec la release plus récente connue, la progression et l'erreur. Minuteur de vérification (`Configure(autoCheck)` ne le réarme que si le réglage change), téléchargement annulable dont la progression est envoyée au plus toutes les 200 ms, état renvoyé après `app.hello` et à chaque changement ; `LaunchPendingInstaller` lance le script de remplacement retenu par `update.apply`. |
| `Bridge/StatusLogFeed.cs` | Commandes `statusLog.*` routées par `HostBridge`. Le journal est lu une fois à la création du pont (échec ajouté à `recovery` de `app.hello`, qui porte aussi les entrées), `statusLog.append` horodate le message et répond `statusLog.added`, `statusLog.clear` répond `statusLog.cleared` ; chaque changement est écrit dans la file d'écriture de la session, vidée à la fermeture. Un échec d'écriture n'est signalé en `error` qu'une fois jusqu'à la prochaine écriture réussie, pour que ce message, lui-même journalisé, ne relance pas une boucle d'échecs. |

## Construction

- `dotnet build backend/Tily.slnx` construit Core, Host, Mcp, Pty et les tests. L'hôte ne construit plus le web : Electron sert `desktop/renderer/dist` (en développement) ou le dossier `desktop/renderer` des ressources de l'application.
- Application Electron (`desktop/`) : `pnpm build` compile le processus principal et le preload TypeScript dans `dist/` (CommonJS) ; `pnpm start` lance Tily avec l'hôte de `backend/src/Tily.Host/bin/Debug/net10.0/Tily` (`TILY_BACKEND` pour un autre exécutable) et l'interface de `desktop/renderer/dist` (`TILY_RENDERER_DEV_URL=http://localhost:5173` pour le serveur Vite). Le processus principal enregistre le schéma privilégié `tily://app/` qui sert l'interface, intercepte `https://tily.files/` pour l'aperçu, refuse toute navigation hors de l'origine de l'interface et toute nouvelle fenêtre, n'accorde que la lecture et l'écriture du presse-papiers, et ouvre la fenêtre maximisée (taille restaurée 1480 × 900). Il intercepte `dialog.pick` (sélecteur natif, réponse `dialog.picked`), `settings.export` et `settings.import` ; tout autre message du web est transmis à l'hôte, toute ligne de l'hôte qui ne commence pas par `{"type":"host.` est transmise au web. La croix, Cmd + Q et le menu Quitter envoient `host.closeRequested` ; l'application se ferme quand l'hôte, après `host.quit`, s'est arrêté (un arrêt inattendu de l'hôte est signalé puis ferme Tily). Le menu macOS porte les rôles Édition (Cmd + C, Cmd + V…) ; les outils de développement n'y sont qu'en développement.
- Publication et paquet : `scripts/build-mac.sh` lit la version de `Tily.Host.csproj`, lance `dotnet publish backend/src/Tily.Host/Tily.Host.csproj -c Release -r osx-arm64 --self-contained -o backend/publish` (`tily-mcp` et `tily-pty` publiés à côté de `Tily`, sans second runtime), construit `desktop/renderer/`, recopie la version dans `desktop/package.json` puis lance `electron-builder` (`desktop/electron-builder.yml`) : l'hôte va dans `Contents/Resources/backend`, l'interface dans `Contents/Resources/renderer`, sortie `desktop/release/Tily-<version>-arm64.dmg`. La signature est ad hoc (`identity: "-"`), sans notarisation : Gatekeeper bloque la première ouverture d'une copie téléchargée depuis le navigateur ; les mises à jour faites par Tily ne sont pas concernées.
- Release : monter `<Version>` dans `Tily.Host.csproj`, puis pousser le tag `v<version>` : la CI construit le `.dmg` et le publie dans la release GitHub (`gh release create … --generate-notes`). Garder le nom `Tily-<version>-arm64.dmg` et le tag `v<version>` : la mise à jour intégrée cherche cet installeur dans la dernière release publiée et affiche la section « Nouveautés » de ses notes.
- CI : `.github/workflows/macos.yml` lance sur `macos-latest` le lint et le build du web, le build d'Electron, `dotnet test backend/Tily.slnx` puis `scripts/build-mac.sh`, publie le `.dmg` en artefact et, sur un tag `v*`, dans la release GitHub.
- Icône : `node scripts/generate-icon.js` (Node seul, aucune dépendance) régénère `desktop/resources/icon.png` (1024 px), versionnée, dont `electron-builder` tire l'icône de l'application ; `web/public/favicon.svg` reprend le même dessin.
- Instance isolée : `TILY_DATA_DIR=<chemin absolu>` fait lire et écrire session, texte, réglages, états d'agents et intégration des shells dans ce dossier. Indispensable pour lancer une version de développement pendant qu'un Tily installé tourne, sans écraser sa session. Les données des panes navigateur restent dans le profil Electron de l'application.

## Conventions

- Messages d'erreur en français (les termes Git restent en anglais et invariables : push, pull, fetch, stash, stage, merge, rebase, amend, checkout, cherry-pick), suffixe `Model` pour les classes de données, suffixe `Async` pour les méthodes asynchrones, aucun commentaire dans le code, fichiers de moins de 400 lignes.
- Les erreurs attendues du pont remontent en `error` au web ; les exceptions inattendues ne doivent pas faire tomber l'hôte.
